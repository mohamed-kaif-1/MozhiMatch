# Recovery procedures

| Failure | Immediate action | Recovery and honesty boundary |
|---|---|---|
| Model quota/network | Show unavailable and preserve raw source/rules | Explicit retry later, no automatic billed provider |
| Invalid model evidence | Mark item needs_review | Inspect prompt/validator with development fixtures, do not salvage a false clear |
| Wrong deployment origin | Keep rules/public shell accessible where possible | Set exact APP_ORIGIN in chosen project and redeploy, no wildcard |
| Build regression | Preserve branch and inspect last working commit | Revert coherent faulty change through reversible Git and rerun affected checks |
| Public URL unavailable | Show local or recording with disclosure | Repair actual URL before final readiness claim |
| Laptop restart | Reopen repo with Node24, npm ci and local env | Current in-memory question work is lost by design. Original examples reload |
| Secret exposed | Stop displaying and disable impacted live access | User rotates affected credential in provider account, then replaces host/local config. Never print it in logs |
| Final gate fails | Freeze current evidence | Report no-go or revise same narrow workflow, never inflate score |

Save a working commit and original example set before final freeze. The roadmap reserves recovery blocks. A local recording can explain intended behaviour during an outage but cannot prove that a live API result occurred. A submission is complete only after the event dashboard shows success and its required links work.
