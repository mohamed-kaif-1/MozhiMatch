# Workbench UX specification

The workbench occupies one route. The header gives name, locale and active processing mode. The introduction says to supply two existing versions and explains the review purpose. Next comes sample loading and an item list. Selecting an item reveals English and Tamil stem/option fields, always explicitly labelled. Add/remove option controls enforce 2–5 slots; Add item stops at ten.

The action area contains source-kind attestation, explicit cloud consent when AI is selected, the mode choice and Analyze. The local/editor mode allows permitted custom practice text. Public hosted mode explains that live AI accepts original demo samples and requires the operator code. Rules can run without cloud consent. Provider notices must describe the active behaviour in ordinary language.

Results appear below or beside the editor after a request. Queue entries show question ID and status. The evidence panel opens the selected field comparison with both snippets, reason label, short model explanation and Keep/Fix/Escalate actions. Decisions are separate from machine status. A manual Keep does not rewrite the model result or remove an unresolved finding from evaluation.

Changing source text immediately marks prior results stale, aborts the client operation and clears machine results and human decisions for the current revision. Switching locale keeps content. Selecting another item keeps the current batch revision. Reset clears all content/results/code after confirmation. Copy issues creates plain text from visible reviewed findings. Nothing is submitted to another person automatically.

Success means the reviewer can identify and act on a specific field. A no-issue result still says that it is machine review of supplied fields. The screen must not imply publication approval or subject-answer correctness.
